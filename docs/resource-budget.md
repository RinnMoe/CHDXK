# 小内存 Docker 部署

目标是运行峰值尽量控制在约 0.5 GB，CHDXK 五个容器的内存硬上限合计 512 MiB（约 537 MB），低于 1 GB。预算不包含宿主 Linux、Docker daemon、外部反向代理、ResHub 或源码构建。

## 默认预算

| 容器 | 内存上限 |
| --- | ---: |
| API（内嵌 Go HTTP 采集器） | 192 MiB |
| PostgreSQL | 192 MiB |
| worker | 48 MiB |
| Redis | 48 MiB |
| 前端 Nginx | 32 MiB |
| 合计 | 512 MiB |

Compose 同时设置 mem_limit 和相同的 memswap_limit，避免靠交换空间掩盖进程超额。API 的 Go 使用软预算 48 MiB、worker 使用 32 MiB，均单核执行。数据库预留 192 MiB 以支持空数据库首次初始化。这些软预算不能替代容器硬限制。达到硬限制时，进程可能被 OOM 终止，任务会失败，不能保证任何数据量都能在此额度内完成。

## 排队与任务

管理员开课同步和个人课程导入共用先进先出调度队列；默认最多 8 个个人导入同时运行（管理员可设置 1～64），队列总容量为 128 项（含运行中的任务）。管理员全校开课同步必须等待已运行的个人任务结束，并独占运行；后续个人任务不会越过管理员任务，避免大批量同步饥饿。排队中没有上游请求、二维码或学校登录态，页面显示前方任务数，可以取消。轮到后才生成二维码，请此时扫码。

排队最多 30 分钟，过期需重新提交；个人任务运行最多 2 小时。连接后前 5 分钟仍未开始同步会释放连接，避免无人扫码或不选择学期占用队列；管理员已开始的批量同步保留原有长任务期限。结束、取消、失败或超时均关闭连接；在旧连接释放前不会运行下一个；不再启动浏览器子进程。重启保留任务进度与学期选择，需重新扫码连接；不恢复排队或学校登录态。

课程详情采集和 worker 并发均为 1。个人并发由超级管理员在后台「运营规则 → 导入设置」中配置，范围 1～64，保存后立即生效并持久化；提高并发会接纳排队任务，降低并发等待运行中的任务结束。教务扫码、手动添加及管理员教务同步可分别启用或禁用；禁用后停止接受新任务，已提交任务继续完成。MyCHU 开关仅控制尚未开放的预留入口。该部署面向单 API 实例，多实例会放大整体并发，不适用此内存预算。

## 数据库和缓存

PostgreSQL shared_buffers=32MB、work_mem=1MB、maintenance_work_mem=16MB、max_connections=20，关闭单查询并行 worker。每个应用进程的连接池最多 6 条、空闲 2 条。

Redis maxmemory=24MB、noeviction，不淘汰会话与任务，满额后写入报错，需要处理积压或增加资源。AOF 保留，关闭定时 RDB 快照以降低常规 fork 频率；仍可能发生 AOF 重写。

## 部署与观察

使用包含本次更改的源码构建；原 v0.1.0 标签不会自动获得这些设置。在 docker/release 下执行：

```bash
docker compose --env-file .env -f compose.yaml build api taskworker frontend
docker compose --env-file .env -f compose.yaml up -d
docker compose --env-file .env -f compose.yaml stats
```

构建阶段不受运行时额度限制，小内存服务器可在其他机器构建镜像后 docker save/load，或使用镜像仓库分发。

观测时区分空闲、扫码等待、个人全学期导入和管理员批量同步，并检查 OOMKilled 和重启次数。约 0.5 GB 是目标，512 MiB 是容器额度总和，不是所有真实任务峰值均低于 0.5 GB 的承诺。

## 并发负载测试（2026-10-08）

在 Linux Docker 的隔离五容器栈中测试，Go 软预算 48 MiB、GOMAXPROCS=1、数据库连接池 6/2。学校响应全部由本地模拟服务提供，不向学校发送并发负载。采集驱动及模拟服务运行在 API 容器内，并额外保留真实 API 进程，因此测量包含测试工具开销。Docker stats 约两秒采样可能遗漏短时峰值，另读取 API cgroup memory.peak 校验。

| 并发 | 采集压力场景 | 五容器采样峰值 | 结果 |
| ---: | --- | ---: | --- |
| 32 | 每用户 17 学期，每学期 1000 教学班、约 1 MB 响应；保留受限报告 | 123 MiB | 全部完成 |
| 64 | 同上，共解析 1088000 条教学班记录；512 MiB 配置（数据库 160 MiB、worker 80 MiB 的测试阶段） | 171 MiB | 全部完成，API cgroup 峰值约 135 MiB，无 OOM/重启 |
| 128 | 同上 | 未完成 | API 达到 192 MiB 限制，测试进程被 OOM 终止 |
| 64 | 每用户 17 学期、每学期 30 门，使用真实 PostgreSQL 匹配、事务写入；512 MiB 配置（数据库 160 MiB、worker 80 MiB 的测试阶段） | 82 MiB | 写入 32640 条记录，全部完成，无 OOM/重启 |

据此采用 64 作为本轮验证支持的个人导入并发上限，不宣称它是所有数据形态下的理论最大值。128 的失败已在独立测试栈复位，未影响其他项目。数据库场景使用隔离 schema、当前 EnrollmentImporter 查询/写入代码和临时课程表；不是整个公网网站的混合流量压测，也不包含学校限流与真实扫码延迟。正式服务器仍需观察实际用户和课程数据。

任务结果保留未匹配课程的准确总数，每学期仅展示前 20 门未匹配明细，每个展示字段最多 128 字。最多保留 128 个用户的临时任务报告；新任务会淘汰较旧的已结束报告，已导入数据库的选课记录不受影响。这防止大量未匹配记录及历史任务把内存无限累积。

## 迁移验证历史

Go 迁移后，完整 API 镜像构建成功，大小约 31.7 MB；非 root 容器内确认没有 Node、Chromium 或 Playwright 目录。隔离五容器空数据库栈空闲合计约 49.5 MiB，真实二维码获取及排队取消检查的采样峰值约 56.4 MiB，未观察到 OOM 或重启。这仍不代表真实全学期采集峰值；并发容量另行负载测试。

在隔离的 Linux Docker 测试栈中，五个容器空闲合计约 56 MiB；生成真实学校登录二维码、验证个人任务排队与取消，再运行 Chromium 渲染 5000 行模拟页面，约两秒间隔采样得到合计峰值约 206 MiB。实际容器额度合计 928 MiB，未观察到 OOM 或重启。这是空数据库与模拟页面测试，尚未验证真实扫码后的全学期个人导入、完整开课同步或多用户网站负载，不能作为生产峰值保证。

迁移前的 Chromium 版本曾因 Debian 依赖下载返回 HTTP 500 而无法完整构建，当时使用旧运行环境替换二进制进行测试。本次已移除该依赖，API、worker 和前端镜像均已从当前源码完整构建成功。

## 后台导入设置验证

在空数据库 Linux Docker 栈实际验证了超管修改并发与各方式开关、非法并发值拒绝、获授站点设置权限的管理员修改返回 403、关闭后扫码和手动添加接口返回 403，以及 API 重启后的设置持久化。队列读取设置安排在建表完成后的请求阶段，避免首次启动访问不存在的表。

首次初始化发现 PostgreSQL 160 MiB 额度会使 pg_jieba 创建进程被终止，因此最终分配调整为数据库 192 MiB、worker 48 MiB（Go 软预算 32 MiB），其余不变，合计仍为 512 MiB。调整后空数据库初始化成功；除验证中主动重启 API 外，没有观察到 OOM 或自动重启。上表采集压力数据保留其原测试分配说明，API 额度仍为 192 MiB。
